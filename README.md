# 净邻洗衣 · 社区自助洗衣房协同处理平台

社区自助洗衣房的**排队预约、故障报修、衣物错拿、超时未取、保洁巡检、物业运营**一体化系统。
居民、客服、保洁、维修、物业五类角色围绕**同一设备订单**协同处理，订单关闭后退款、维修、错拿申诉、遗留物、用户信用全部进入档案，支撑物业的扩容、定价与限流决策。

## 原始需求

> 设计社区自助洗衣房排队故障与衣物错拿页面，可使用 Vue 3、TypeScript 和 Pinia。居民扫码预约洗衣机或烘干机时，页面显示设备容量、剩余时间、预约队列、价格、洗涤模式、消毒状态和保洁记录。用户开机后，页面记录支付、设备编号、洗涤程序、结束提醒和取衣倒计时。若用户超时未取、设备中途停机、烘干不干、洗衣液不足、衣物错拿、门锁打不开或用户要求退款，页面要让用户、客服、保洁、维修和物业围绕同一设备订单处理。保洁巡检时记录地面、滤网、洗衣液、异味、遗留衣物和摄像头状态。订单关闭后，退款、维修、错拿申诉、遗留物保管和用户信用进入档案，便于物业判断是否增加设备、调整价格或限制恶意占用。页面还要覆盖会员套餐、夜间洗衣噪声、设备清洁、洗涤用品补货、保洁代取授权和物业纠纷。洗衣房是公共空间，页面需要让用户占用、设备状态和物业处理保持一致。当洗衣房位于宿舍、公寓或老旧小区时，噪声、用水、排队和卫生诉求不同，页面需要支持不同运营规则。设备扩容建议会结合投诉和真实使用率。对于多设备门店，页面还要支持设备分区、错峰价格、夜间静音模式和长期占用限制，帮助物业平衡收益与邻里关系。

## 技术栈

| 层 | 技术 |
| --- | --- |
| 前端 | Vue 3 + TypeScript + Pinia + Vue Router + Vite（手写设计系统 CSS，无 UI 框架依赖） |
| 后端 | Node.js 20 + Express + pg（原生 SQL，启动时自动建表/播种） |
| 数据库 | PostgreSQL 16（compose 内部网络，不发布宿主端口） |
| 部署 | 多阶段 Dockerfile（非 root + HEALTHCHECK）+ docker compose |

## 一键启动（验证方式 = 宿主 docker compose up）

```bash
cp .env.example .env        # 可选，默认即可；CC_PUBLISH_PORT 由环境注入
docker compose up -d --build
docker compose ps           # 等待 app 健康检查通过
docker compose port app 3000   # 查看实际映射端口（如 0.0.0.0:3088）
```

浏览器访问 `http://localhost:<CC_PUBLISH_PORT>`（本环境为 `http://localhost:3088`）。

验证结束后释放资源：

```bash
docker compose down          # 加 -v 可同时清空数据卷
```

## 演示数据（开箱即有）

- **3 家门店 3 种运营规则**：宿舍（青松苑，23:00 静音/晚高峰加价）、公寓（蓝湾，夜间仅静音机可启动/白天错峰 85 折）、老旧小区（幸福里，21:30 静音/信用门槛 70/取衣宽限 60 分钟）
- **12 台设备**（分区管理）：含运行中、待取衣、故障（QS-D202）、维修中（LW-W201）、离线（XF-D201）、静音机型
- **进行中业务**：运行中订单、待取衣订单（12 分钟后超时）、排队订单、错拿申诉、洗衣液不足工单、噪声投诉
- **历史档案**：40+ 笔历史订单（利用率统计）、退款、维修、信用变动、巡检、遗留物

## 关键业务流（建议按角色依次体验）

1. **居民预约全流程**：登录 `resident1` → 设备看板（容量/剩余时间/队列/价格/消毒/保洁记录）→ 预约 → 支付（会员折扣/错峰价自动计算）→ 启动 → 倒计时与结束前 5 分钟提醒 → 取衣
2. **超时未取闭环**：`resident1` 的待取衣订单超时后 → 自动扣信用、生成保洁工单 → `cleaner1` 代收 → 衣物入遗留物柜、设备释放 → 居民在「我的-遗留物」认领
3. **故障协同**：居民上报「烘干不干/中途停机/门锁打不开」→ 工单自动路由维修 → `repair1` 登记维修/远程开锁 → 设备恢复
4. **退款审批**：居民申请退款 → `service1` 在工单内批准 → 原路退回（模拟）并归档
5. **错拿申诉**：`resident1` 的错拿工单 → 客服受理 → 物业核实后可调信用 → 归档
6. **保洁巡检**：`cleaner1` 提交巡检（地面/滤网/洗衣液/异味/遗留/摄像头）→ 异常自动生成工单
7. **物业看板**：`property1` 查看利用率/投诉分布 → 扩容建议（结合投诉与真实使用率）→ 调整错峰价格/静音时段/占用限制 → 新增设备

## 状态一致性保障

- 后端 15 秒周期任务：未支付 10 分钟自动取消、到点自动完成（等价设备 IoT 回调）、结束前 5 分钟提醒、超时标记+扣信用+生成保洁工单、设备状态校正
- 设备占用（运行/待取）期间不可被下一位启动；取衣或代收后才释放并通知队列下一位
- 夜间静音时段非静音机型禁止启动；信用低于门槛/有超时未处理订单/超每日上限均无法预约（防恶意占用）

## 目录结构

```
├── Dockerfile              # 多阶段：前端构建 → 后端依赖 → 非 root 运行时（HEALTHCHECK）
├── docker-compose.yml      # app + postgres（db 不发布宿主端口）
├── .env.example
├── server/                 # Express API：routes / jobs(周期任务) / seed(演示数据)
└── web/                    # Vue3 + TS + Pinia 前端
```

## 主要 API

`POST /api/auth/login`、`GET /api/sites/:id/board`（设备看板）、`POST /api/orders`（预约）、`pay/start/pickup/cancel`、`POST /api/devices/:id/callback`（设备回调）、`POST /api/orders/:id/report`（问题上报）、`/api/tickets/*`（工单协同）、`/api/refunds/*`、`/api/inspections`、`/api/cleaner/tasks`、`/api/lost-items/*`、`/api/maintenance/board`、`/api/stats/overview|suggestions`、`PUT /api/sites/:id/rules`、`/api/archives`
